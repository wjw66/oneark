# OneArk · 个人资产沉淀系统 — 产品白皮书

**版本：0.2 讨论稿（由「个人工作资产系统」升级）**
**产品形态：跨平台本地优先桌面应用**
**核心入口：会议、笔记与日常材料（高频入口）**
**命名：OneArk —— 一个方舟，装下完整的你；资产归你、整船带走、永不沉没**

## 摘要

每个人每天在会议、笔记、学习、创作与生活中产生大量材料，却散落在企业系统、聊天工具、云端服务和个人临时文件里。它们帮助完成当下的事，却很难沉淀为个人可迁移、可复用、可持续增长的资产。

OneArk 提出「个人资产沉淀系统」的产品模型：以会议、笔记与日常材料为高频入口，在用户控制的本地项目空间中保存原始材料，通过转写、结构化、检索与生成，把一次性内容转化为可持续积累的个人资产。系统不把 AI 对话作为中心，而把**原始证据、人工确认与资产可迁移性**作为中心。工作只是其中的一舱——学习、创作、生活与关系同样在此沉淀。

产品采用 local-first 原则：默认在本地完成捕获、保存与基础转写；用户可主动选择云端或自定义模型服务，但系统必须透明呈现数据外发边界。长期目标不是替用户建一个封闭的「第二大脑」，而是让用户拥有一个可以理解、修订、备份、迁移和导出的个人资产空间。

## 1. 问题定义

### 1.1 个人信息的短暂性
会议、讨论、灵感与学习是密集的信息来源，但结束后往往只留零散记忆与不稳定的记录。素材虽在，却缺乏检索与关系——任务、决策、知识之间从未被连起来。

### 1.2 个人资产与平台的错位
企业知识库与协作系统服务组织流程，不一定服务个人长期发展。用户换团队、离职或迁移工具后，原本参与形成的经验和工作脉络可能无法继续使用。

### 1.3 生成式 AI 的信任问题
云端 AI 工具可快速生成摘要和文档，但用户往往无法完整控制：原始材料保存在哪里；哪些内容被发送到模型服务；生成结果能否追溯到原始材料；数据能否批量导出；供应商停止服务后资产是否仍然可用。

因此，产品问题不是「如何再做一个聊天界面」，而是：

> 如何让个人内容在不牺牲隐私和可迁移性的前提下，被可靠地保存、理解、检索和再次生产。

## 2. 产品命题

> 每一次记录，都不应只变成一条转瞬即逝的笔记，而应沉淀为一组可验证、可关联、可迁移的个人资产。

资产的形成过程：

```text
原始材料（音频 / 笔记 / 导入）
  -> 原始转写 / 解析
  -> 人工可修订的文本
  -> 决策、任务、主题、关系
  -> 可检索的知识资产
  -> 日报、周报、汇报、PPT、HTML 等工作产物
```

AI 的作用是降低整理和生成成本，而不是替用户决定什么是真实事实、什么应当进入长期记忆。

## 3. 设计目标与非目标

### 3.1 设计目标
1. **资产归用户控制**：项目数据可复制、备份、迁移与导出。
2. **证据可追溯**：派生内容能回到原始材料、转写片段与生成任务。
3. **默认本地处理**：不依赖云端也能完成捕获、保存与基础转写。
4. **人工确认可介入**：用户可修订转写、确认任务、控制长期记忆写入。
5. **渐进式智能化**：先解决保存与检索，再引入 Agent 与复杂自动化。
6. **跨平台可用**：以 macOS 与 Windows 为第一批桌面目标。

### 3.2 非目标
- 一开始就构建通用 Agent 平台；
- 用知识图谱替代基础全文检索；
- 强制所有模型调用经过 Agent；
- 在没有真实用户需求前实现通用插件市场；
- 默认把用户数据同步到云端；
- 同时覆盖所有来源与所有音频设备。

## 4. 核心概念模型

### 4.1 项目空间
项目空间是用户可见、可复制的资产边界，包含结构化数据库与可读文件。会议、笔记与导入的材料都进入同一套 capture 结构。

```text
项目空间/
├── project.json
├── workspace.sqlite
├── capture/
│   └── item-id/
│       ├── metadata.json
│       ├── source.wav / source.md
│       ├── transcript.raw.json
│       └── transcript.edited.json
├── knowledge/
├── tasks/
└── exports/
```

SQLite 保存实体、关系、索引和任务状态；原始文件与导出保存在文件系统。数据库中的附件路径使用相对路径，以保证项目可以移动。

### 4.2 原始资产与派生资产
- **原始资产**：录音/原件、原始转写、模型版本、时间戳和导入文件；
- **派生资产**：修订文本、摘要、任务、标签、知识条目和对外产物。

派生资产不能覆盖原始资产。生成结果应保存来源引用、模型配置和生成时间，便于判断与回溯。

### 4.3 事实、推断和建议
区分：材料直接提供的**事实**、从材料提取的**结构化信息**、模型的**推断与建议**、用户确认后的**长期资产**。只有用户确认后的内容，才能进入高置信度的长期知识或任务视图。

## 5. 产品机制

### 5.1 捕获与沉淀机制（会议为旗舰入口）
选择/创建项目 → 录音或导入 → 保存原始材料 → 后台创建转写/解析任务 → 本地模型处理 → 展示结果与时间戳 → 用户修订与确认。一期以会议为旗舰入口，不做实时转写，先验证更基础的资产闭环。

### 5.2 知识沉淀机制
会议、Markdown、文档与笔记都可进入知识空间。先提供来源、标签、关联与全文检索，再逐步引入语义检索与记忆能力。知识写入采用「建议 + 确认」模式：AI 可建议归类，但绝不在用户不知情时永久写入。

### 5.3 工作产物机制
产物优先从已确认的资产生成，采用模板、字段与来源引用控制输出。日报、周报、纪要、PPT、HTML、信息图、流程图是不同渲染目标，不应混成一个不透明的 Agent 输出。

### 5.4 Agent 机制
Agent 是跨模块编排层，不是底层数据与模型服务的替代品。确定性能力由应用服务直接提供（捕获、转写、保存、搜索、导出、固定模板渲染）；Agent 处理需规划、检索、多步工具调用与用户确认的任务，例如依据一周材料生成周报草稿并列出每条结论的来源。

## 6. 信任与隐私模型

### 6.1 Local-first 的含义
Local-first 不等于永远不联网，而是：本地存储是默认路径；原始材料不要求先上传；本地转写可独立完成；远端模型必须由用户主动配置；外发内容、provider 与 endpoint 应可见。

### 6.2 云端模型边界
用户选择远端模型时，系统需明确提示：发送的是原始转写还是修订文本、是否含音频、使用哪个 provider、失败重试是否会再次发送、返回结果如何写入本地。API key 不应作为普通项目文件复制；项目数据默认不是加密容器，后续可按需增加系统密钥管理、文件级加密或 SQLCipher。

### 6.3 可迁移性
用户应能在不依赖在线服务的情况下，获得原始材料、原始与修订转写、元数据、知识条目、任务、生成产物，以及来源与版本信息——这正是 OneArk「方舟」隐喻的落脚点：一舟承载，整船带走。

## 7. 技术实现原则

### 7.1 桌面应用
Go + Wails + React/Vite。Go 负责项目空间、文件系统、SQLite、任务与 Python worker 生命周期；React/Vite 负责编辑器、设置、列表与状态呈现。不使用 Next.js 的 SSR——一期是本地桌面应用。

### 7.2 转写运行时
一期采用 Go 控制、Python 推理的进程边界：Go 创建转写任务 → Python worker 加载 faster-whisper → 输出进度、错误与结果 → Go 写入 SQLite 并通知 UI。未来加入实时转写，可先扩展长驻 streaming worker。

### 7.3 模块化策略
一期采用模块化单体，而非通用插件运行时。仅为稳定变化点定义接口：`CaptureSource`、`TranscriptionProvider`、`ProjectStore`、`GenerationService`、`Exporter`。插件、MCP 与 A2A 需在权限、生命周期、版本与审计模型明确后再开放。

## 8. 演进路线

路线不是功能清单，而是依赖关系：

```text
P0 技术可行性
  -> P1 沉淀闭环（以会议为旗舰入口）
  -> P2 检索与确认
  -> P3 工作产物
  -> P4 Agent 编排
  -> P5 同步、生态与商业化
```

- **P0**：验证录音权限、材料保存、项目空间、Python worker 打包、长音频转写与失败恢复。
- **P1**：创建项目、捕获、批量转写、修订、搜索并导出；不做实时转写、知识图谱与 Agent。
- **P2**：文档导入、全文检索、来源、标签、关联，以及用户确认后的结构化抽取。
- **P3**：日报、周报、纪要与汇报模板，多格式可编辑可导出，保留产物来源。
- **P4**：受控权限下检索资产、调用工具、生成草稿、执行多步工作流；高影响操作需确认且可审计。
- **P5**：热点追踪、云同步、团队能力、高级记忆、硬件与 Pro 模型。

## 9. 评价标准

产品成功不以「支持多少模型或协议」衡量，而以沉淀闭环是否可信衡量：

1. 用户能在短时间内完成一次捕获并找到对应转写；
2. 长音频与异常中断不会导致资产丢失；
3. 原始内容、修订内容与生成内容可以区分；
4. 用户可以按关键词、来源与项目回溯内容；
5. 项目目录可以备份、移动与导出；
6. 用户清楚知道哪些内容被发送到远端模型；
7. 生成产物能够回到具体来源，而不是只能相信模型。

## 10. 主要风险

- **跨平台捕获差异**：macOS 与 Windows 的权限、系统音频与设备行为不同，先固定一期支持的来源与录音范围。
- **模型质量与资源成本**：本地模型带来下载体积、CPU/GPU、首启与版本管理问题；按需下载并记录版本，结果溯源到模型配置。
- **过早平台化**：通用插件、Agent、MCP、A2A 与知识图谱会扩大复杂度，应在 P1/P2 形成真实使用频率后再引入。
- **许可证与模型权利**：发布前逐项审核桌面框架、FFmpeg、模型权重、推理库、前端依赖与第三方 Agent 运行时的许可及再分发条件。

## 11. 结论

OneArk 的长期价值，不在于把最多的 AI 功能堆在一个应用里，而在于建立一个可信的个人资产底座：原始材料被保存，派生结果可追溯，用户拥有确认权，项目可以迁移，AI 可以逐步参与但不会取代事实与控制权。

> 把每一次记录，可靠地沉淀为属于你自己的个人资产。

当这个承诺被真实用户反复验证，个人资产库、工作台、Agent、MCP / A2A 与内容生产能力才有稳定的数据基础与产品理由——而这一切，都装载在属于你自己的方舟里。
